Independent review verification policy: focused.

Assess the relevant code thoroughly. Before running a verification command,
identify the suspected finding it checks and what would confirm or falsify it.
Prefer code tracing, a small reproduction, or an existing test selected by name.
Do not run a repository-wide test suite, build, lint sweep, benchmark, broad
integration bundle, or aggregate target such as make check for general confidence.
These limits also apply to review skills and any delegated work. Permission for
full-suite validation in a later synthesis stage does not apply to this review.

Run checks in the foreground, with at most 60 seconds per command and 300 seconds
of cumulative verification time in this review, including setup and waiting.
Use a bounded timeout, such as timeout --signal=TERM --kill-after=5s 60s COMMAND,
shortened to the remaining allowance. Do not repeat a timed-out or failed check
with a larger timeout, broaden it to a suite, or move retries to background tasks.
Do not fix the repository or launch paid reviews/smoke tests as verification.

Before a check, inspect its documented dependencies and output locations. Use
already permitted temporary storage for caches/fixtures where supported. A
read-only checkout does not imply writable scratch. Do not relax sandbox policy
or install dependencies to make tests run; report the specific limitation instead.

These allowances limit verification commands, not the code assessment itself.
For stateful recovery claims, attempt a focused reproduction when dependencies
and permitted scratch are available, including the surrounding orchestration and
shared error handling. Otherwise give a per-finding explanation for inspection-only
evidence and its remaining uncertainty; read-only source alone is not proof that
all checks are unavailable.
If a check fails, times out, or needs unavailable dependencies, continue with the
available evidence and finish the review. State which commands actually ran,
their outcomes, and any verification gaps. Do not treat a timeout as a defect,
invent passing results, or present an unverified suspicion as an established bug.

Environment-blocked verification:
Inspect test fixtures and documented prerequisites before running checks: pytest,
unittest, make, or scripts may invoke Docker/Podman indirectly. A container CLI
being installed does not prove that container networking or a daemon is usable.
If setup fails because of an unavailable daemon, nested-container restrictions,
read-only sysctls, or missing permissions, record the command and actual error.
Stop equivalent attempts with the same unmet prerequisite; continue checks that
can run. Reuse supplied blocker evidence for this candidate and environment;
switching reviewer, model, or synthesis stage is not a reason to retry it. Do not escalate privileges, change host configuration, or modify the
application solely to bypass the review environment. Distinguish genuine product
or fixture defects from environmental failures using code and other evidence.
An environment failure alone is not a blocking code finding or a reason to ask
for implementation repairs. It is also not a passing test. Describe remaining
uncertainty and give exact manual verification commands, their required environment
(e.g. a host with working container networking), and expected success criteria.
Do not silently skip required checks or claim a green suite from partial results.
